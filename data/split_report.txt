  NOTE on the per-fold patient/trial counts (this is the honest, easy-to-
  misread part): dev-train and dev-validation are a stratified 80/20 split of
  the SAME 130 development pairs, so they intentionally SHARE patients and
  trials. Every dev-validation patient and trial is a subset of dev-train's.
  That is why:
     - dev-train alone already covers all 26 dev patients / 22 dev trials, and
     - the pooled DEV counts (26 patients / 22 trials) equal dev-train's, NOT
       the sum of the two folds.
  dev-validation is for over-fitting detection during tuning, NOT a
  generalization claim. The generalization claim rests on the trial-disjoint
  TEST set only.

======================================================================
PAPER SPLIT DESCRIPTION (copy into manuscript)
======================================================================
  The dataset is partitioned at the trial level into a development set
  (130 pairs, 26 patients, 22 trials) and a held-out test set
  (270 pairs, 45 patients, 18 trials), disjoint in both patients and trials
  (verified: 0 patient overlap, 0 trial overlap). Framework tuning (prompt
  refinement, thresholds, the refinement loop) uses the development set only,
  further split 80/20 (stratified by label, seed 2026) into dev-train
  (104 pairs; 26 patients, 22 trials) for tuning and dev-validation
  (26 pairs; 18 patients, 14 trials, a subset of dev-train) for configuration
  selection and over-fitting detection. The test set is evaluated after the
  framework configuration is frozen.
